# Coolify deployment

Use `deploy/coolify/compose.yaml` as the Docker Compose file in a Git-based Coolify application. Keep the base directory at `/` so the web and public-site Docker build contexts can read the repository root.

The stack starts a new PostgreSQL database, the EnvanterTR application, and the public marketing/demo site. The web application and public Nginx service share a private Compose network so `/giris` and `/api` can reach the app; PostgreSQL is on that same non-published network. It uses three explicitly named, EnvanterTR v1-specific persistent volumes for database contents, uploaded company media, and ASP.NET data-protection keys. Those volume names are independent of the Coolify project/resource slug, so a similarly named legacy service cannot silently supply its database or files. Do not rename them to legacy volume names or point this stack at another application's database.

## Request traffic and GitHub are separate

Customer browsers connect to the configured `envantertr.com` domain, which Coolify routes to `public-site`; Nginx sends application routes to `web`, and `web` talks to PostgreSQL on the private Compose network. Normal page views, sign-ins, inventory operations, and customer uploads are served by this server stack. They do not start GitHub Actions jobs or consume GitHub Actions minutes. GitHub stores the source and sends a deployment change signal; Coolify fetches/builds a new revision when a deployment is triggered. If no deployment runs, the currently deployed revision continues serving traffic.

The repository's `EnvanterTR CI` workflow is separate from Coolify deployment. It runs on pushes to `main` and pull requests targeting `main`, subject to GitHub account/plan limits. A failed or quota-blocked CI run means that CI check did not complete; it does not by itself stop the already-running Coolify stack. Do not add a payment method just to keep the existing website serving requests. If included Actions capacity is exhausted, wait for its reset or use a separately approved runner/deployment process; paid usage is an account billing choice, not a prerequisite for ordinary customer traffic.

Database schema changes are a separate operational step. The application does not automatically apply pending migrations during normal startup; take and verify a backup, then explicitly run the approved migration procedure before expecting an older production database to match a newer application schema.

Coolify generates `SERVICE_PASSWORD_64_POSTGRES` and `SERVICE_PASSWORD_64_SETUP` for the database password and one-time initial-owner setup token. Keep both values in Coolify's environment-variable store. The bootstrap token is required to create the first owner and should be removed from the application environment after setup. SMTP variables are optional and can be added later for email delivery.

In Coolify, add both `envantertr.com` and `*.envantertr.com` to the `public-site` service on port 80 after the stack is deployed and verified. The wildcard domain needs a matching wildcard DNS record pointing at the Coolify proxy, plus a TLS certificate that covers `*.envantertr.com` (normally configured through the DNS provider's ACME DNS challenge). The default host serves the public marketing/demo site; wildcard company hosts are proxied to the company app. Nginx preserves the requested host and forwards app/API requests to the private `web` service. The PostgreSQL service has no public port.

The wildcard route only establishes the HTTP/TLS path. Nginx serves `envantertr.com` and `www.envantertr.com` from the public marketing/demo site; only other matching subdomains use the company app proxy. A company owner/admin sets its unique subdomain under Company settings → Company profile. The app resolves a tenant subdomain against the active company's slug and binds both login and authenticated sessions to that company. Session cookies are shared across this deployment's subdomains so a renamed tenant can move to its new URL; server-side tenant checks still reject use on another company's host. Confirm that the matching company slug exists and that account membership/role checks permit the user before customer acceptance. Do not treat DNS resolution alone as a live tenant being ready. After deployment, verify the wildcard host's TLS certificate, login page, `/api/status`, and a tenant-scoped authenticated request. The repository contains no Coolify credentials, and production routing must be configured in Coolify and the DNS provider separately.

### Wildcard 503 diagnosis

For a Git-based Compose application, configure both `https://envantertr.com` and `https://*.envantertr.com` as domains on the Compose `public-site` service, targeting its container port `80`, then redeploy the Coolify resource so the proxy receives the route. The public-site Nginx wildcard server then forwards tenant requests to `web:8080` while preserving the host. A successful apex request proves only that the apex route works; it does not prove the wildcard route exists.

If a wildcard URL returns HTTP 503 with `no available server`, the request has reached Coolify's HTTPS proxy but the proxy has no healthy matching upstream for that configured hostname. First inspect the deployed resource's Domains list and deployment/service health, then inspect Coolify proxy logs. Do not start by changing application credentials or tenant data. If apex and wildcard both fail, also check the proxy target port and `public-site` health. The repo Nginx config was locally exercised with `Host: firma.envantertr.com` and returned the web app's `/api/status`; this test proves the in-stack proxy path only, not the external Coolify route.

For a read-only external readiness report, run `node tools/Check-CoolifyProduction.mjs` from the repository root. It checks the apex and a representative tenant `/api/status`, distinguishes pending database migrations from Coolify's plain-text `503 no available server`, and exits nonzero unless both hosts report `ready` with zero pending migrations. It never logs response bodies, credentials, or customer data. This check does not modify Coolify, the database, or customer state; a clean report is a prerequisite signal, not a replacement for authenticated tenant-scope acceptance. CI runs `Verify-CoolifyProductionReadiness.mjs` against synthetic HTTP responses for the healthy, migration-pending, proxy-503, malformed-response, and network-failure cases; CI does not poll the live domains.
