# Recoverable company deletion — candidate acceptance, 25 October 2026

## Scope and production boundary

Implements the missing ordinary administration capability needed by Hedef 20.9.5: a new demo tenant can be removed and recovered without removing another tenant or the shared Identity account. This does **not** prove the real Demo3/Santa/Farma scenario, provider acceptance, or completion of Hedef.

Production remains `5790980f8f8a298b720287260a37b7f972bd1e57`, schema 120. This candidate adds migration 121 and has **not** been deployed. A new production backup, isolated restore and rollback rehearsal, migration rehearsal, complete CI and server staging remain release gates.

## Behavior

- Root platform administration only, with the existing password/MFA freshness and CSRF requirements. The 600-second proof lifetime is unchanged.
- DELETE `/api/platform/companies/{companyId}` requires the exact company slug and an 8–1000 character reason. The transaction sets `DeletedAt` and disables access; it does not remove tenant records, memberships, media, Identity accounts or financial history.
- Only that company's sessions and API tokens are revoked. A shared user's password, security stamp and sessions/tokens in another company remain unchanged.
- Current directory/CSV default excludes deleted companies; `deleted=true` exposes the trash. Trash rows offer restore rather than activation; bulk activation cannot bypass trash. The platform group also rejects ordinary company-specific writes until restoration.
- POST `/api/platform/companies/{companyId}/restore` records a reason and leaves access suspended. Revoked credentials remain revoked. Billing and provider subscriptions are not changed by either action; the form states this explicitly.
- Actor and company scoped `CompanySoftDeleted` / `CompanyRestored` audit records are saved in the same transaction. Repeat deletion does not duplicate the audit.
- Migration 121 adds one nullable column and an inactive-when-deleted constraint. No destructive Up or Down is provided; operational rollback uses verified backups. Existing slugs remain reserved.
- CI now checks pull requests with any base branch so stacked PR #25 is covered without changing its base.
