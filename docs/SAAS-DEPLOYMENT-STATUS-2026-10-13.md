# SaaS tenant-host check — 13 October 2026

## Production observation

Read-only requests to `https://firma.envantertr.com/` and `/api/status` returned HTTP 503 with body `no available server`. A later check on 13 October again returned 503 for both tenant paths while `envantertr.com` and `www.envantertr.com` returned HTTP 200. The tenant DNS A/AAAA answers resolve to Cloudflare edge addresses; the 503 includes `Server: cloudflare` and a `CF-RAY` request identifier (`a49e72747f4ac13c-AMS`). This establishes that the tenant hostname reaches Cloudflare but has no responding upstream route at the edge. It does not identify whether the Coolify proxy, origin host, service health, or domain binding is the failing upstream component. No production credentials or origin address are available in this repository.

## Repository cause and local fix

The Coolify public Nginx configuration previously had only a catch-all marketing-site server. It had routes from the marketing domain into the app for `/giris` and `/api`, but no wildcard tenant server; a tenant root would therefore have used the public marketing fallback if Coolify routed it there. Added an explicit `*.envantertr.com` server that forwards tenant paths and the original `Host` to the private `web:8080` service. A follow-up host-routing check found that this wildcard also matched `www.envantertr.com`; the marketing server now explicitly names `envantertr.com` and `www.envantertr.com` ahead of the wildcard, so only company subdomains enter the app. An isolated Nginx container on the local Compose network returned marketing content for both public names and the app login page for `firma.envantertr.com`. Company admins can now set a validated, unique tenant slug from the company profile. Login resolves the active company's slug from the request host, and authenticated requests recheck the same slug against their company membership. Coolify shares the protected session cookie across its subdomains to support URL changes; company/role validation still runs on each request. Isolated security acceptance scenarios cover valid tenant login, wrong-company selection, reserved/duplicate slug rejection, persistence, and cross-subdomain session rejection. The Coolify guide calls for attaching both the root and wildcard domains to `public-site`, setting wildcard DNS and a wildcard-covering TLS certificate, then checking login, app health, and authenticated tenant scope.

`tools/Verify-CoolifyTenantRouting.mjs` checks the wildcard server, upstream, host/forwarded headers, upload limit, setup guidance, and preserved marketing fallback. `tools/Verify-TenantSlugProfile.mjs` locks the company URL setup and session-boundary contract into CI. All 39 JavaScript UI/API verifiers passed on the current branch. The focused isolated PostgreSQL security suite passed its 3 tenant-host login, slug validation/persistence, and session-isolation cases. The real `nginx:alpine` image accepted the routing configuration with `nginx -t` (a test-only `web` host entry satisfied Nginx's static upstream lookup).
